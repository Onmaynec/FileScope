# Политика репозитория FileScope

Версия: **1.0**  
Дата вступления в силу: **5 августа 2026 года**

Эта политика дополняет Policy Pack Veilbyte. При расхождении применяется более строгое правило, если владелец Veilbyte письменно не установил исключение.

## Классификация

- **Видимость:** Public
- **Классификация:** Public Source-Available
- **Жизненный цикл:** Active
- **Стабильность API и форматов:** Pre-1.0
- **Официальная организация:** `Veilbyte`
- **Окончательное решение:** `@Onmaynec`

Публичный доступ к исходному коду не делает FileScope open source. Права использования определяются исключительно файлом `LICENSE`.

## Назначение

FileScope — Windows desktop-приложение для предварительного локального анализа файлов, HTTP/HTTPS URL и архивов до запуска. Проект предназначен для законной защиты пользователя и собственной инфраструктуры.

Использование регулируется `RESPONSIBLE_USE.md`. FileScope не должен применяться для несанкционированного доступа, распространения вредоносного ПО, перехвата чужих данных, нарушения доступности сторонних систем или иных противоправных действий.

## Ветки

- `main` — стабильные опубликованные версии;
- `develop` — интеграция проверенных изменений следующей версии;
- `feature/*` — новые возможности;
- `fix/*` — исправления;
- `release/*` — подготовка релизов;
- `hotfix/*` — срочные исправления опубликованной версии;
- `chore/*` — инфраструктура, зависимости и управление репозиторием.

Изменения в `main` и `develop` выполняются только через Pull Request. Force push и удаление этих веток запрещены.

## Pull Request и review

Каждое изменение кода, документации, CI или политики должно быть связано с Issue, кроме очевидной мелкой правки.

Пока FileScope поддерживается одним активным разработчиком, допускается 0 независимых одобрений при одновременном выполнении всех условий:

- изменение проходит через Pull Request;
- все обязательные CI-проверки успешны;
- шаблон PR заполнен;
- риски и ручная проверка описаны;
- автор выполняет self-review перед слиянием.

После появления независимых reviewers применяются значения по умолчанию:

- обычные изменения — 1 одобрение;
- безопасность, сеть, архивные парсеры, обновления, лицензия, GitHub Actions, сборка и релизы — 2 одобрения либо явное решение владельца.

Все review threads должны быть разрешены до слияния.

## Стратегия слияния

- `feature/*`, `fix/*`, `chore/*` — squash merge;
- `release/*`, `hotfix/*` — merge commit;
- rebase merge не используется как стандартный способ.

Коммит в защищённой ветке должен отображаться как Verified. Conventional Commits: тип на английском, описание на русском.

## Обязательные проверки

Перед слиянием применимых изменений выполняются:

- ESLint;
- TypeScript strict typecheck;
- frontend unit-тесты;
- production frontend build;
- Playwright smoke-тесты;
- проверка контраста интерфейса;
- `cargo fmt --all --check`;
- Rust unit-тесты;
- `cargo check`;
- Tauri production build для релизных изменений;
- Windows x64 и NSIS packaging для релизов;
- проверка policy-файлов;
- анализ зависимостей и секретов, когда соответствующие функции доступны.

## Безопасность и данные

Запрещено добавлять в Git:

- токены, ключи, пароли, cookies и сертификаты подписи;
- персональные данные и неочищенные пользовательские пути;
- приватные конфигурации и полные сетевые дампы;
- реальные вредоносные образцы;
- активные вредоносные URL;
- код, права на который не принадлежат автору.

Обнаруженный секрет считается скомпрометированным и должен быть немедленно отозван.

## Зависимости

Новая зависимость должна быть обоснована в PR. Для неё проверяются:

- назначение и необходимость;
- активность сопровождения;
- лицензия;
- известные уязвимости;
- влияние на размер, приватность и поверхность атаки.

High или Critical уязвимость без исправления допускается только по документированному решению владельца с компенсационными мерами.

## Релизы

Используется Semantic Versioning и теги `vMAJOR.MINOR.PATCH`.

Официальный релиз должен:

- происходить из `main`;
- соответствовать защищённому тегу;
- иметь release notes на русском языке;
- содержать SHA-256 для бинарных артефактов;
- использовать сборки официального GitHub Actions workflow;
- явно описывать ограничения и security-изменения.

Автоматическая публикация разрешена только workflow с минимальными `permissions`.

## Экстренный bypass

Владелец может обойти обычный процесс только для срочного восстановления работоспособности или устранения угрозы. После bypass обязательно создаётся или обновляется Issue/PR, описывается причина, запускаются пропущенные проверки и проводится последующий review.
