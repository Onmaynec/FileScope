# Участие в разработке FileScope

Спасибо за интерес к FileScope. Перед началом прочитайте `README.md`, `LICENSE`, `REPOSITORY_POLICY.md`, `SECURITY.md`, `RESPONSIBLE_USE.md` и `CODE_OF_CONDUCT.md`.

FileScope является Public Source-Available проектом. Публичность исходного кода не предоставляет права использовать, изменять или распространять его вне условий `LICENSE`.

## Что можно предлагать

- исправления воспроизводимых ошибок;
- новые функции, заранее согласованные через Issue или Discussion;
- улучшения документации и доступности;
- тесты, линтеры и улучшения CI;
- улучшения производительности и безопасности;
- безопасные искусственные тестовые образцы.

Уязвимости нельзя отправлять через публичный Issue или обычный Pull Request. Используйте `SECURITY.md`.

## Процесс работы

1. Создайте или найдите Issue, если изменение не является очевидной мелкой правкой.
2. Используйте fork либо рабочую ветку при наличии доступа.
3. Создайте ветку от актуальной `develop`:
   - `feature/*` — новая функция;
   - `fix/*` — исправление;
   - `chore/*` — инфраструктура и зависимости;
   - `release/*` — подготовка версии;
   - `hotfix/*` — срочное исправление стабильного релиза.
4. Делайте небольшие логически завершённые коммиты.
5. Используйте Conventional Commits: тип на английском, описание на русском.
6. Подписывайте коммиты так, чтобы GitHub показывал статус Verified.
7. Добавьте или обновите тесты, документацию и CHANGELOG.
8. Запустите локальные проверки.
9. Откройте Pull Request в `develop` и заполните шаблон полностью.
10. Устраните замечания review, разрешите все threads и дождитесь обязательных проверок.

Примеры коммитов:

```text
feat: добавить проверку цифровой подписи
fix: исправить обработку повреждённого PE
security: ограничить глубину вложенных архивов
docs: обновить правила поддержки
test: добавить сценарий Unicode-гомографа
chore: обновить конфигурацию CI
```

## Перед созданием Pull Request

Проверьте локальное окружение:

```bash
pnpm doctor
```

Установите только зафиксированные зависимости:

```bash
pnpm install --frozen-lockfile
```

Frontend:

```bash
node --check scripts/doctor.mjs
pnpm --filter @filescope/desktop lint
pnpm --filter @filescope/desktop typecheck
pnpm --filter @filescope/desktop test
pnpm --filter @filescope/desktop build
pnpm --filter @filescope/desktop test:e2e
```

Rust:

```bash
cd apps/desktop/src-tauri
cargo fmt --all --check
cargo test --locked
cargo check --locked
```

Нативная production-сборка Windows:

```bash
pnpm --filter @filescope/desktop build:desktop
git diff --exit-code -- pnpm-lock.yaml apps/desktop/src-tauri/Cargo.lock
```

`pnpm-lock.yaml` и `apps/desktop/src-tauri/Cargo.lock` являются частью проверяемого исходного состояния. Не обновляйте их вручную и не используйте `--no-frozen-lockfile` для обычной разработки или CI. Изменение lock-файлов должно быть связано с осознанным изменением manifest-файлов и описано в PR.

Результаты выполненных и пропущенных проверок обязательно указываются в Pull Request. Нельзя заявлять об успешном тесте, если он не запускался.

## Требования к коду

- TypeScript strict mode;
- Rust-код должен проходить `rustfmt`, тесты и `cargo check --locked`;
- нативные вызовы изолируются от UI;
- анализируемые объекты не запускаются без отдельного утверждённого дизайна sandbox;
- пассивный URL-анализ не должен выполнять скрытые сетевые запросы;
- любое активное сетевое действие требует явного согласия пользователя;
- архивные парсеры обязаны применять ограничения размера, глубины и числа записей;
- пользовательские значения экранируются при HTML-экспорте;
- смысл состояния не передаётся только цветом;
- светлая тема должна сохранять контраст текста не ниже WCAG AA для обычного текста;
- пользовательские тексты ведутся на русском с подготовкой к локализации;
- код должен быть понятным, поддерживаемым и тестируемым.

## Зависимости

Новая зависимость должна быть обоснована в PR. Укажите:

- какую проблему она решает;
- почему существующих средств недостаточно;
- состояние сопровождения;
- лицензию;
- влияние на размер приложения и поверхность атаки;
- известные уязвимости и меры снижения риска.

Копирование кода с несовместимой или неизвестной лицензией запрещено.

## AI-сгенерированный код

AI-assisted код допускается, только если автор:

- понимает его работу;
- проверил происхождение и лицензионные риски;
- проверил отсутствие секретов и опасных конструкций;
- добавил или обновил тесты;
- несёт за изменение ту же ответственность, что и за написанный вручную код;
- раскрыл существенное использование AI в Pull Request.

Непроверенный или непонятный автору AI-код не принимается.

## Безопасные тестовые материалы

Запрещено добавлять:

- реальные вредоносные образцы;
- стилеры, RAT, кейлогеры, ransomware и загрузчики;
- активные вредоносные URL;
- чужие данные и неочищенные логи;
- приватные ключи, токены и сертификаты подписи.

Для тестирования используются искусственные структуры, повреждённые заголовки, зарезервированные домены и безопасные mock-данные.

## Pull Request

PR должен содержать:

- цель и связанную задачу;
- перечень изменений;
- влияние на архитектуру и безопасность;
- выполненные тесты;
- известные ограничения;
- новые зависимости;
- скриншоты для UI-изменений;
- шаги ручной проверки;
- план отката для критичных изменений;
- подтверждение CLA.

## Review и merge

Пока проект поддерживается одним активным разработчиком, допускается self-review через PR после успешного CI. После появления независимых reviewers:

- обычные изменения требуют 1 одобрение;
- безопасность, сеть, криптография, архивные парсеры, updater, Actions, build и release требуют 2 одобрения либо явное решение владельца.

Стратегия:

- `feature/*`, `fix/*`, `chore/*` — squash merge;
- `release/*`, `hotfix/*` — merge commit;
- rebase merge не используется как стандартный способ.

## Лицензионные условия вклада

Отправляя Pull Request, вы подтверждаете, что имеете право предоставить вклад и принимаете `CONTRIBUTOR_LICENSE_AGREEMENT.md`. Вы сохраняете авторство, но предоставляете владельцу Veilbyte права, необходимые для использования, изменения, распространения, коммерциализации и перелицензирования вклада в составе проекта.

PR без подтверждения CLA может быть отклонён.

## Документация

Документация проекта, Issues, Pull Requests, коммиты и release notes ведутся на русском языке. Технические идентификаторы, имена API и общепринятые термины могут оставаться на английском.


## Fuzzing и private triage

Fuzz corpus не должен содержать malware, active malicious URLs, secrets или пользовательские файлы. Быстрые property tests обязательны для security-sensitive изменений. Потенциальный security crash оформляется через Private Vulnerability Reporting; публичный Issue допускается только после устранения чувствительных деталей и оценки affected versions.
