# FileScope v0.4.0 — release preflight и QA evidence

Финальный release preflight работает fail-closed. Команда `pnpm release:preflight` предназначена только для момента, когда Windows manual QA и extended fuzz уже подтверждены.

Для обычной разработки используется `pnpm release:preflight:development`: он проверяет release notes, manifests, readiness boundary и структуру evidence-template, но не принимает release evidence как подтверждение готовности.

После фиксации реальных автоматических evidence используется `pnpm release:preflight:automated`. Этот режим требует настоящий Windows artifact SHA-256 и минимум два подтверждённых extended fuzz run, проверяет exact validated SHA и metadata-only tail, но намеренно разрешает `manualQa=false`. Его успешное завершение означает: **автоматизируемая часть release gates закрыта, остаются только реальные Windows manual QA gates**.

## Финальный evidence

По умолчанию release workflow ожидает файл `.github/release-evidence/v0.4.0.json`. В качестве основы используется `docs/releases/v0.4.0-evidence.example.json`.

Evidence содержит:

- `validatedHeadSha` — release-candidate commit, на котором реально выполнялись Windows CI/artifact build и exact-head extended fuzz;
- `windowsArtifact.name` — `FileScope-Windows-x64`;
- `windowsArtifact.sha256` — SHA-256 проверенного Windows artifact;
- `operator` и `checkedAt`;
- шесть `manualQa` gates, которые остаются `false` до фактического ручного выполнения;
- минимум два независимых `extendedFuzzRuns`.

Для каждого extended run обязательны уникальный `runId`, `runAttempt`, `event`, `ref`, exact `headSha`, все пять fuzz targets, `secondsPerTarget >= 180`, `conclusion=success` и `crashArtifacts=0`.

PR fuzz использует 20 секунд на target и никогда не считается extended release evidence. Extended evidence разрешён только от `schedule`, `workflow_dispatch` или dedicated release-candidate push. Push evidence принимается исключительно с `refs/heads/fuzz-release-candidate`. Хотя бы один trusted extended run (`workflow_dispatch` или dedicated candidate push) обязан совпадать с `validatedHeadSha`.

## Dedicated release-candidate fuzz branch

В `.github/workflows/security-fuzz.yml` существует специальный trigger для ветки `fuzz-release-candidate`. Эта ветка не является production/release branch и не должна содержать собственных изменений: она лишь указывает на уже существующий commit из `feature/v0.4.0`/release candidate.

Создание или fast-forward этой ветки запускает тот же read-only cargo-fuzz workflow с extended budget 180 секунд на каждый target. Это позволяет получить exact-head evidence даже когда API-клиент не предоставляет `workflow_dispatch`, не ослабляя permissions и не превращая обычные PR runs в release evidence.

## Fuzz evidence artifact

`Security fuzz smoke` использует 20 секунд на target для pull request и 180 секунд на target для `schedule`, `workflow_dispatch` и dedicated candidate push.

После успешного extended run workflow создаёт metadata-only artifact `FileScope-fuzz-evidence-<run id>` с `run.json`. Он содержит run ID/attempt, event/ref, head SHA, budget, conclusion, crash artifact count и точный список targets. Metadata artifact не содержит corpus/input payload и хранится не более трёх дней согласно общей fuzz-artifact policy; после проверки значения переносятся в постоянный release evidence JSON.

Crash inputs создаются только при failure и также хранятся не более трёх дней. Security-sensitive crash не публикуется публично с exploit details — используется private triage policy.

## Разрешённый metadata-only хвост после validatedHeadSha

QA evidence невозможно добавить в тот же commit, SHA которого оно подтверждает. Поэтому preflight разрешает validated commit быть предком текущего release HEAD, но только если после него изменены исключительно:

- сам release evidence JSON;
- `docs/releases/v0.4.0.md`;
- `CHANGELOG.md`;
- `.github/release-request.json`;
- `docs/product/v0.4.0-readiness-checklist.md` как status-only checklist.

Любое изменение production source, tests, workflow, lockfile, manifests или другой документации после `validatedHeadSha` блокирует automated/final preflight и требует нового exact-head QA/evidence.

## Последовательность автоматического закрытия

1. Зафиксировать release-candidate source HEAD и дождаться зелёных Policy/CI/PR fuzz.
2. Получить минимум два independent extended fuzz run по 180 секунд на каждый target; хотя бы один — exact-head trusted run через `workflow_dispatch` или `fuzz-release-candidate`.
3. Зафиксировать run metadata и SHA-256 Windows artifact в `.github/release-evidence/v0.4.0.json` с manual flags=`false`.
4. Выполнить `pnpm release:preflight:automated`. Он обязан пройти полностью.
5. После этого изменение production source снова открывает автоматические release gates и требует нового validated SHA.

## Последовательность финального GO после manual QA

1. Выполнить реальный Windows manual QA: migration v0.3.x, process-kill publication, ACL/lock, DPAPI second-user/PC, portable и full-clear restart.
2. Перевести соответствующие шесть `manualQa` flags в evidence на `true` только после фактического выполнения.
3. Добавить финальную секцию `## [0.4.0]` в CHANGELOG и release metadata без изменения validated source.
4. Запустить `pnpm release:preflight`. Любой незакрытый gate должен завершить команду ошибкой.
5. Только после успешного final preflight разрешён release workflow из `main`.
