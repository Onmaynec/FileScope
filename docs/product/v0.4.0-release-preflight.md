# FileScope v0.4.0 — release preflight и QA evidence

Финальный release preflight работает fail-closed. Команда `pnpm release:preflight` не должна использоваться как обычная development-проверка: она предназначена только для момента, когда Windows QA и extended fuzz уже подтверждены.

Для CI и разработки используется `pnpm release:preflight:development`. Этот режим проверяет release notes, manifests, readiness boundary и структуру evidence-template, но принципиально не засчитывает ручные QA gates.

## Финальный evidence

По умолчанию release workflow ожидает файл `.github/release-evidence/v0.4.0.json`. В качестве основы используется `docs/releases/v0.4.0-evidence.example.json`.

Перед финальным preflight заполнить:

- `validatedHeadSha` — commit, на котором реально выполнялись Windows QA и exact-head manual extended fuzz;
- `windowsArtifact.name` — `FileScope-Windows-x64`;
- `windowsArtifact.sha256` — SHA-256 протестированного Windows artifact;
- `operator` и `checkedAt`;
- все шесть `manualQa` gates только после фактического выполнения;
- минимум два независимых `extendedFuzzRuns`.

Финальный preflight запрещает принимать `false` в manual QA и требует минимум два успешных extended run с разными `runId`. Для каждого run обязательны все пять fuzz targets, `secondsPerTarget >= 180`, `conclusion=success` и `crashArtifacts=0`.

Хотя бы один extended run обязан быть запущен через `workflow_dispatch` на точном `validatedHeadSha`. Это не позволяет заменить финальную проверку накопившимися PR smoke runs.

## Fuzz evidence artifact

`Security fuzz smoke` использует 20 секунд на target для pull request и 180 секунд на target для `schedule`/`workflow_dispatch`.

После успешного extended run workflow создаёт metadata-only artifact `FileScope-fuzz-evidence-<run id>` с `run.json`. Он содержит run ID/attempt, event, head SHA, budget, conclusion, crash artifact count и точный список targets. Metadata artifact не содержит corpus/input payload и хранится не более трёх дней согласно общей fuzz-artifact policy; после проверки значения необходимо перенести в постоянный release evidence JSON.

Crash inputs также создаются только при failure и хранятся не более трёх дней. Crash artifact нельзя прикладывать к публичному issue с exploit details; используется private triage policy.

## Разрешённый metadata-only хвост после validatedHeadSha

QA evidence невозможно добавить в тот же commit, SHA которого оно подтверждает. Поэтому final preflight разрешает validated commit быть предком текущего release HEAD, но только если после него изменены исключительно:

- сам release evidence JSON;
- `docs/releases/v0.4.0.md`;
- `CHANGELOG.md`;
- `.github/release-request.json`.

Любое изменение production source, tests, workflow, lockfile, manifests или другой документации после `validatedHeadSha` блокирует release и требует нового QA/evidence на новом commit.

## Последовательность финального GO

1. Зафиксировать release-candidate code HEAD и дождаться зелёных Policy/CI/PR fuzz.
2. Выполнить реальный Windows manual QA, включая migration, process-kill, ACL/lock, DPAPI second-user/PC, portable и full-clear restart.
3. Выполнить минимум два extended fuzz runs; хотя бы один `workflow_dispatch` — на exact release-candidate SHA.
4. До истечения трёхдневного retention скачать metadata `run.json` успешных extended runs и перенести значения в release evidence.
5. Записать SHA-256 реально протестированного Windows artifact.
6. Добавить release evidence и финальную changelog/release metadata без изменения production source.
7. Запустить `pnpm release:preflight`. Любой незакрытый gate должен завершить команду ошибкой.
8. Только после успешного preflight разрешён release workflow из `main`.
