# Репутация и ложные срабатывания Windows

Этот документ описывает обязательный процесс для официальных Windows-релизов FileScope.

## Почему новый EXE может получить срабатывание

Антивирусные движки и Microsoft Defender используют не только сигнатуры известных угроз, но и машинное обучение, распространённость файла, репутацию издателя и другие эвристические признаки. Поэтому новый или редко встречающийся неподписанный EXE иногда получает единичное ложное срабатывание даже при воспроизводимой сборке и открытом исходном коде.

Один внешний вердикт не является частью локального Rule Engine FileScope. Изменение внутренних правил анализа не может напрямую изменить решение Microsoft Defender или другого поставщика.

## Обязательные меры перед публикацией

1. Собрать installer и portable EXE только в утверждённом GitHub Actions workflow.
2. Проверить, что оба файла используют Windows GUI subsystem.
3. Подписать все публикуемые Windows-бинарные файлы одним доверенным сертификатом Authenticode или Microsoft Artifact Signing.
4. Не изменять файл после подписи.
5. Проверить подпись средствами Windows.
6. Сформировать `SHA256SUMS.txt` после окончательной подписи.
7. Прикрепить к одному GitHub Release подписанные файлы и соответствующие контрольные суммы.
8. Сохранить идентификатор workflow run, commit, тег, SHA-256 и сведения о сертификате.

## Обработка ложного срабатывания Microsoft

При подтверждённом ложном срабатывании:

1. Не переименовывать и не перепаковывать уже опубликованный файл скрыто.
2. Проверить SHA-256 и сопоставить файл с официальным workflow run.
3. Отправить файл через Microsoft Security Intelligence submission portal в категории разработчика программного обеспечения.
4. Указать название продукта, версию, ссылку на официальный репозиторий и описание назначения приложения.
5. Сохранить submission ID в приватном журнале релиза или разрешённом Issue без чувствительных данных.
6. Дождаться решения поставщика и повторно проверить тот же SHA-256.
7. При необходимости выпустить новую PATCH-версию; существующий тег и бинарные файлы не перезаписывать.

## Что не считается исправлением

- отключение полезной функции только ради изменения хеша;
- обфускация или упаковка бинарного файла;
- переименование EXE без изменения содержимого;
- удаление защитных предупреждений из собственного анализатора;
- заявление о безопасности только на основании результата одного агрегатора;
- скрытая замена файла в уже опубликованном релизе.

## Правила FileScope для PE

FileScope v0.3.1 разделяет признаки по силе:

- отсутствие Authenticode — низкий контекстный признак;
- одиночный `VirtualAlloc`, `ShellExecuteW` и аналогичные API — информационный контекст;
- несколько связанных функций работы с чужим процессом — предупреждение;
- полная цепочка выделения памяти, записи и удалённого запуска — высокий риск;
- сочетание сетевой загрузки и запуска — высокий риск.

Статический анализ не заменяет проверку доверенности подписи, репутацию издателя, поведенческий анализ и защиту операционной системы.
