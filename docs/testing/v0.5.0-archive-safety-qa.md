# FileScope v0.5.0 — Windows Archive Safety Core QA

Статус: manual release gate для development-ветки `feature/v0.5.0`.

Цель: подтвердить на Windows 10/11 x64, что ZIP-анализатор FileScope корректно показывает Windows-specific path semantics и неполноту анализа, не извлекая и не запуская содержимое архива.

## Предусловия

- использовать production Tauri/NSIS build с exact head проверяемого release candidate;
- выполнять проверку на локальном NTFS-диске;
- не использовать реальные вредоносные образцы — только синтетические ZIP fixtures;
- сохранить JSON-экспорт каждого сценария с неожиданным результатом;
- при проверке сетевой тишины убедиться, что активная URL-проверка не запускается параллельно.

## Инварианты безопасности

Для каждого ZIP-сценария должны одновременно выполняться условия:

- содержимое ZIP не запускается;
- содержимое ZIP не извлекается на диск;
- анализ ZIP не создаёт сетевых запросов;
- выбранный ZIP не модифицируется;
- SHA-256, central-directory traversal и local-header metadata относятся к одному открытому объекту;
- техническая неполнота или encryption flag сами по себе не повышают Risk Score;
- cancel/timeout/limits обрабатываются backend, а не только визуально в UI.

## UI и экспорт

Проверить для ZIP-02, ZIP-10, ZIP-13 и ZIP-14:

- UI показывает число total/scanned entries без подмены одного другим;
- partial report не отображается как полный «признаков угроз не найдено»;
- JSON содержит `displayPath`, `path`, `rawNameHex`, `pathNormalizationChanged`, `windowsPathKey` и применимые safety flags;
- JSON содержит `entriesScanned`, `summaryComplete`, `unreadableEntries` и aggregate counters;
- HTML/JSON export не ломается на `<`, `>`, `&`, кавычках, bidi/control и Unicode именах;
- длинные имена и evidence не нарушают layout; evidence остаётся bounded.

## Проверка отсутствия extraction / execution

1. Перед анализом сделать snapshot каталога, где расположен fixture, и `%TEMP%`.
2. Запустить только ZIP-анализ FileScope.
3. После анализа сравнить содержимое каталогов: новых extracted payload-файлов быть не должно.
4. Для fixture с `.exe`, `.cmd`, `.ps1` убедиться через Process Explorer/Process Monitor, что дочерний процесс из ZIP не создавался.
5. Для symlink fixture убедиться, что target не читался как отдельный объект и не materialize на диске.

## Проверка сетевой тишины

Во время локального ZIP-анализа:

- не запускать ручную активную URL-проверку;
- через Resource Monitor/Process Monitor/Wireshark убедиться, что ZIP-анализ не инициирует DNS/HTTP/TCP;
- наличие фоновых запросов WebView/ОС не считать запросом анализатора без привязки к процессу/стеку FileScope.

## Cancel и resource budgets

- запустить синтетический ZIP с большим количеством entries;
- отменить анализ во время traversal;
- UI должен дождаться backend-confirmed cancellation и не показывать успешный verdict;
- повторить с уменьшенным `maximumArchiveEntries` и убедиться, что результат `StoppedByLimit`, а не malware verdict;
- проверить, что limits нельзя полностью отключить через UI/IPC.

## Release acceptance

Manual gate считается пройденным только если:

- ZIP-01…ZIP-18 соответствуют ожидаемой семантике;
- ни один fixture не извлечён и не запущен;
- ZIP-анализ не инициирует сеть;
- Windows NFC/NFD fixture ZIP-10 подтверждён на реальном Windows runner/desktop;
- JSON и HTML export сохраняют честный контекст и не ломаются на hostile names;
- production NSIS build устанавливается/запускается на Windows 10 и Windows 11 x64;
- exact release-candidate head проходит GitHub CI, Policy и Security fuzz;
- после интеграции v0.4.0 выполнен финальный version sync `0.5.0` и повторный exact-head CI.

Результаты manual gate фиксировать в PR #85 отдельным комментарием с версией Windows, SHA release-candidate commit и отметками PASS/FAIL по каждому ID.
