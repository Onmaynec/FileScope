# Релизная политика FileScope

## Версионирование

FileScope использует Semantic Versioning и теги `vMAJOR.MINOR.PATCH`.

До версии 1.0:

- `MINOR` может включать существенные изменения функциональности и внутренних форматов;
- `PATCH` используется для совместимых исправлений и security-fix;
- breaking changes должны быть явно описаны в release notes.

## Поток релиза

```text
feature/*, fix/*, chore/*
          ↓
       develop
          ↓
   release/X.Y.Z
          ↓
         main
          ↓
 tag vX.Y.Z + GitHub Release
```

Hotfix создаётся от `main`, проверяется через PR и возвращается одновременно в `main` и `develop`.

## Условия публикации

Перед релизом обязательны:

- закрытый release checklist или Issue;
- актуальный CHANGELOG;
- успешные ESLint, TypeScript, unit и Playwright проверки;
- успешные `cargo fmt --all --check`, `cargo test` и `cargo check`;
- Tauri production build;
- Windows x64 и NSIS packaging;
- ручная проверка installer и portable EXE;
- security-review сетевых, архивных, updater и CI-изменений;
- подтверждение версии во frontend, Cargo и Tauri-конфигурации;
- отсутствие незаполненных policy-маркеров и секретов.

## Официальные артефакты

Официальными считаются только артефакты, которые:

- созданы GitHub Actions в `Veilbyte/FileScope`;
- связаны с commit из `main` и тегом версии;
- опубликованы в GitHub Release;
- сопровождаются `SHA256SUMS.txt`;
- не были вручную заменены после проверки без нового документированного workflow run.

## Release notes

Release notes ведутся на русском языке и включают:

- основные возможности;
- исправления;
- изменения безопасности и приватности;
- breaking changes;
- известные ограничения;
- поддерживаемые ОС и архитектуры;
- инструкции проверки SHA-256.

## Каналы

- `Latest` — последняя стабильная версия;
- `Pre-release` — alpha, beta и release candidate;
- `develop` и Actions artifacts — тестовые сборки, не являющиеся официальным релизом.

## Права публикации

Релиз публикует владелец либо явно назначенный участник с ролью Developer или выше. Workflow публикации должен использовать минимальные `permissions` и защищённый GitHub Environment, когда он настроен.

## Откат

При критической проблеме:

1. релиз помечается предупреждением или снимается с Latest;
2. создаётся `hotfix/*` и security/bug Issue;
3. пользователям публикуется безопасная рекомендация;
4. исправление проходит сокращённый, но документированный PR-процесс;
5. выпускается PATCH-версия, а не перезаписывается существующий тег.

Существующие теги и опубликованные бинарные файлы не заменяются скрыто.
